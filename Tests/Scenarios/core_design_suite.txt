# CelestialLighting core-design live suite — every scenario here runs inside ONE RimWorld load.
#
#   ../RimWorldTestHarness/Runner/run_test.sh \
#       --suite Tests/Scenarios/core_design_suite.txt \
#       --mod . --mod TestMod
#
# (Both --mod flags are required: the first activates the mod under test, the second the probe
# bridge. Passing only the bridge loads probes whose typerefs into CelestialLighting cannot resolve,
# and every Probe step throws "Could not resolve type ... CelestialLighting.SolarPosition".)
#
# WHAT IS AND ISN'T SAFE TO BATCH. The harness reloads the save between scenarios whose residue a
# soft reset cannot undo, but as of this writing its planner only forces a reload for MAP residue —
# a scenario leaving a GameCondition behind is followed by a soft reset, which cannot unregister it.
# Measured, not assumed: with the eclipse scenarios in this list, eclipse_ramp_flyin read the eclipse
# eclipse.json had started (coverage 1.0 instead of its own 0.2257). So every condition-driven
# scenario is deliberately NOT here and must be run as its own process:
#
#   for s in daylight_inertness eclipse eclipse_ramp_flyin eclipse_ramp_flyout aurora blood_moon \
#            natural_eclipse natural_eclipse_trigger sky_blackout_gate \
#            sky_blackout_eclipse_carveout unnatural_darkness_gate vacuum_eclipse vacuum_eclipse_frames; do
#     ../RimWorldTestHarness/Runner/run_test.sh Tests/Scenarios/$s.json --mod . --mod TestMod
#   done
#
# Weather scenarios ARE safe to batch, because each sets the weather it wants before probing, so the
# previous scenario's leftover front cannot colour its readings.
#
# Also not here: the moon-dependent scenarios (moon_illumination, moon_survey, moon_shadow_visibility,
# moon_shadow_twilight_fade, night_radiance, pitch_black_nights, cloud_cover_albedo_cavity). Moon
# phase is a function of the absolute tick, so their expected values only hold at the fixture's own
# tick — inside a suite the preceding scenarios have already jumped the clock, which is exactly how
# an earlier suite run reported night_radiance as failing while it passed standalone. Run those on
# their own too.
#
# cloud_cover_albedo_cavity.json picked its day (52, not day 40 -- see the scenario's own
# description) specifically FOR a near-full moon, because the fix it verifies only shows up on the
# night floor and a fuller moon gives the cavity gain more absolute glow to amplify. That deliberate
# choice is exactly what a drifted clock inside a suite would wreck.
#
# moon_shadow_twilight_fade is doubly tick-sensitive: §6b makes shadow strength depend on the SUN's
# elevation as well as the moon's, so a drifted clock moves both terms of the ratio at once.

# --- weather: each sets its own, so they need no reload between them ---
weather_dimming_census.json

# It pins absolute dimming fractions, which scale with §13's strength knob (the preset's
# weatherDimming value). They are pinned against the shipped default and move together if a preset
# default changes — a run where every row is low by the same ratio is that, not a classifier
# regression. Every probe in it reads at noon, which is what keeps it safe here.
#
# weather_dimming.json is NOT here, and the ladder is not why: its first seven probes agree with the
# census exactly. Its last four do not. They read sky_glow and purkinje at hour 2, and night sky glow
# carries a moonlight term, so it belongs with the moon-dependent scenarios above for the reason
# given there — SetSeason and SetTime fix the day-of-year and hour but not the absolute tick, and the
# moon is a function of the tick.
#
# Measured 2026-07-30: in-suite it read sky_glow 0.0817 against a pinned 0.1419 with purkinje
# correspondingly high (§9 keys rod vision on a darker apparent sky), and 0.1455 standalone minutes
# later in the same build. Run it on its own:
#
#   ../RimWorldTestHarness/Runner/run_test.sh Tests/Scenarios/weather_dimming.json --mod . --mod TestMod
#
# The census keeps the ladder covered here — 40 probes across 20 weather types against
# weather_dimming's 7 — so dropping it from the suite costs no §13 coverage, only the feature-toggle
# A/B and the blizzard frames, both of which are visual checks rather than cadence checks.
#
# penumbra_lowsun.json is deliberately absent: it builds a wall grid and repaints terrain
# (ScenarioResidue.Map), and it is still in-flight work whose expected softness (0.5367) does not
# match what the current build reads at its chosen hour (0.0920). Run it standalone while that is
# being settled.

# vacuum_night_floor.json belongs with the moon-dependent scenarios above and NOT in this list, which
# is worth stating explicitly because it reads like a candidate: its residue (NewMap | Map) is
# reload-required, and SuitePlanner does isolate it correctly and automatically, so isolation is not
# what disqualifies it. Its moon_illumination and moon_elevation pins are — moon phase is a function
# of the absolute tick, and a soft reset restoring TicksGame is not enough to reproduce the fixture's
# own tick once earlier scenarios have moved the clock.
#
# Measured rather than assumed, 2026-07-30: added here and run, it failed with moon_illumination
# 0.1795 against a pinned 0.0364 and both moon_elevation pins out by 6-7 degrees, while passing
# standalone in the same build minutes later. Its off-noon sun_elevation went with them (-16.29
# against -9.033) and its midnight one was exact, which is the clock moving, not the latitude.
#
# The gap it was added to close is real and still open: nothing runs this file on a cadence, which is
# how a pin ce6bdbf invalidated sat broken across five merges. Closing it wants a per-scenario
# absolute-tick anchor, not a line in this list.
